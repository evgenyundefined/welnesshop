# agelesscode

Витрина для каталога wellness-устройств, пептидов, витаминов, beauty-продуктов,
инъекционных препаратов и ингаляторов: каталог с фильтрами, регистрация и вход,
корзина, оформление заказа с выбором доставки и страница оплаты. Плюс админка:
категории и товары (CRUD), покупатели (редактирование и блокировка), заказы (CRUD).

Laravel 13 + Vue 3 (SPA) + Tailwind 4. Отдельный проект, без связи с другими репозиториями.

## Запуск в Docker

Стек: nginx + php-fpm + MySQL + Redis. Нужен только Docker.

```bash
cp .env.example .env
docker compose up -d --build
```

Открыть `http://localhost:8000`.

Первый запуск занимает несколько минут: образ собирается, а entrypoint
доставляет зависимости, генерирует `APP_KEY`, накатывает миграции, заливает
каталог и собирает фронтенд. Последующие старты пропускают уже сделанное.
Прогресс видно в `docker compose logs -f app`.

Полезные команды:

```bash
docker compose exec app php artisan test
docker compose exec app php artisan migrate:fresh --seed
docker compose exec app npm run build
docker compose exec mysql mysql -uwellness -psecret wellness
docker compose exec redis redis-cli
docker compose down -v          # снести вместе с данными
```

Порты и доступы переопределяются в `.env`: `APP_PORT`, `FORWARD_DB_PORT`,
`FORWARD_REDIS_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`.

На Linux, если UID хоста не 1000, соберите образ под свой:
`UID=$(id -u) GID=$(id -g) docker compose up -d --build` — иначе файлы,
записанные контейнером, окажутся под чужим владельцем.

Воркер очередей в стек не входит: приложение пока ничего не ставит в очередь,
хотя `QUEUE_CONNECTION=redis` уже настроен.

## Деплой в продакшен

`docker-compose.yml` из предыдущего раздела — для разработки: он монтирует
исходники с хоста, ставит зависимости при старте и публикует порты MySQL и
Redis наружу. Для боевого сервера есть отдельный `docker-compose.prod.yml`:

- код, зависимости и собранный фронтенд лежат внутри образов, хост-каталог не
  монтируется;
- наружу торчит только nginx, база и Redis доступны лишь внутри сети compose;
- сертификат Let's Encrypt выпускает и продлевает сервис `certbot`, nginx сам
  переключается на https, как только сертификат появляется;
- `APP_DEBUG=false`, `APP_ENV=production`, secure-куки, доверие прокси
  платформы (иначе Laravel не увидит HTTPS и сломает редиректы и куки);
- загруженные фото товаров лежат на именованном томе и переживают передеплой,
  nginx отдаёт их напрямую;
- при старте прогоняются миграции и заводится администратор из переменных
  окружения; демо-каталог из PDF заливается только при `SEED_CATALOG=true`.

### 1. Ключ приложения

`APP_KEY` задаётся переменной окружения, а не генерируется в контейнере: иначе
каждый передеплой выдаёт новый ключ и разлогинивает всех разом. Сгенерируйте
один раз и сохраните — если PHP под рукой:

```bash
php artisan key:generate --show
```

Если нет, подойдёт любой контейнер с PHP: ключ — это 32 случайных байта в
base64, ничего специфичного для Laravel в нём нет.

```bash
docker run --rm php:8.4-cli php -r "echo 'base64:'.base64_encode(random_bytes(32)).PHP_EOL;"
```

Контейнер не стартует без `APP_KEY` и скажет об этом в логе.

### 2. Переменные

Скопируйте `.env.production.example` и заполните: `APP_KEY`, `APP_URL` (боевой
домен), `SERVER_NAME`, `CERTBOT_EMAIL`, `DB_PASSWORD`, `DB_ROOT_PASSWORD`,
`SHOP_ADMIN_EMAIL`, `SHOP_ADMIN_PASSWORD`. Пароли не должны остаться
дефолтными: `secret`, `root` и `Password1` из dev-конфигов в бою недопустимы.

### 3. Сборка образов

Секции `build:` вынесены в отдельный оверлей `docker-compose.build.yml`, чтобы
`docker-compose.prod.yml` оставался пригодным там, где исходников на хосте нет
(панель Portainer, например). Локальная сборка и запуск:

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.build.yml build
docker compose -f docker-compose.prod.yml -f docker-compose.build.yml up -d
```

### 4. Развёртывание через Portainer

Portainer разворачивает стек тремя способами, и от выбора зависит, где
собираются образы.

**Реестр + Web editor (рекомендуется).** Собираете образы у себя, пушите в
реестр, а в панели работаете только с готовыми тегами — на хосте ничего не
собирается, деплой быстрый и повторяемый.

```bash
export APP_IMAGE=registry.example.ru/wellness-shop-app:1.0.0
export NGINX_IMAGE=registry.example.ru/wellness-shop-nginx:1.0.0

docker compose -f docker-compose.prod.yml -f docker-compose.build.yml build
docker push "$APP_IMAGE"
docker push "$NGINX_IMAGE"
```

Дальше в Portainer: **Stacks → Add stack → Web editor**, вставить содержимое
`docker-compose.prod.yml`, ниже в **Environment variables** добавить пары из
`.env.production.example` (включая `APP_IMAGE` и `NGINX_IMAGE`), **Deploy the
stack**. Если реестр приватный — сначала **Registries** и учётка для него.

**Repository.** Portainer клонирует репозиторий на хост и собирает образы сам:
указать URL, ветку и в *Compose path* — `docker-compose.prod.yml`, а в
дополнительных путях `docker-compose.build.yml`. Тогда реестр не нужен, но
сборка идёт на боевом хосте: `npm ci` и `composer install` съедают память и
время при каждом обновлении стека.

При обновлении такого стека переключатель **Re-pull image** должен быть
выключен: образов `wellness-shop-*` нет ни в одном реестре, и попытка их
скачать завершает деплой ошибкой `pull access denied` ещё до сборки.

Важнее другое: `docker compose up` собирает образ, только если его ещё нет.
После правки кода образ с тем же тегом остаётся старым, поэтому перед
обновлением стека удалите `wellness-shop-app` и `wellness-shop-nginx` в разделе
**Images** — или соберите с явным `docker compose ... build`, если есть SSH.

**Upload** ведёт себя как Web editor: контекста сборки нет, нужны готовые
образы.

Переменные с синтаксисом `${VAR:?...}` — обязательные: если не заполнить,
Portainer откажет в деплое с явной ошибкой, а не поднимет стек с пустым
паролем.

### 5. HTTPS

Сертификат выпускает сервис `certbot` по схеме webroot: certbot кладёт файл в
том `certbot-webroot`, nginx отдаёт его по `/.well-known/acme-challenge/`,
Let's Encrypt забирает его по домену. Ручных шагов нет, но порядок такой:

1. **A-запись домена уже должна указывать на IP сервера.** Пока DNS не
   разошёлся, проверка не пройдёт: certbot повторит пять раз с минутной паузой,
   потом уйдёт в 12-часовой цикл и попробует снова.
2. Заполните `SERVER_NAME` (все имена через пробел — их же получит сертификат)
   и `CERTBOT_EMAIL`. Порт 80 должен остаться открытым и после выпуска: по нему
   проходит продление.
3. Первый выпуск лучше сделать с `CERTBOT_STAGING=1`. Браузер такому
   сертификату не поверит, зато лимит Let's Encrypt — пять неудачных выпусков
   на домен в час — не сгорит на опечатке в DNS. Как только в логе `certbot`
   появится `Successfully received certificate`, уберите переменную и
   передеплойте стек: тестовый сертификат продлевается через тестовый же
   сервер, поэтому certbot при старте увидит его, удалит и запросит боевой.

Что именно лежит на томе, видно снаружи — в логе это не написано:

```bash
echo | openssl s_client -connect agelesscode.store:443 -servername agelesscode.store 2>/dev/null |
  openssl x509 -noout -issuer
```

`O = Let's Encrypt` — боевой, `CN = (STAGING) …` — тестовый.

nginx стартует без сертификата на чистом http и раз в минуту заглядывает на
том. Как только сертификат появился, он перечитывает конфигурацию сам: 80-й
порт начинает отдавать редирект на https, 443-й — сайт. Перезапускать ничего не
нужно, в логе nginx появится `configuration reloaded`.

Продление идёт в том же контейнере дважды в сутки. Let's Encrypt обновляет
сертификат за 30 дней до истечения, nginx подхватывает новый файл в течение
минуты.

Проверить со стороны:

```bash
curl -I http://agelesscode.store     # ожидаем 301 на https
curl -I https://agelesscode.store    # ожидаем 200
docker compose -f docker-compose.prod.yml logs certbot | tail -30
```

Если нужно запретить браузерам ходить по http вообще, добавьте в 443-й
server-блок `add_header Strict-Transport-Security "max-age=31536000" always;`.
Решение не бесплатное: браузер запомнит запрет на год, и вернуться на http для
этого домена уже не выйдет.

### 6. После первого запуска

Админка открывается по `/admin` под `SHOP_ADMIN_EMAIL` и
`SHOP_ADMIN_PASSWORD`. Отдельной формы смены пароля администратора нет: он
заводится сидером, который при каждом старте обновляет запись по e-mail, —
чтобы сменить пароль, поменяйте переменную и перезапустите сервис.

Схема в `APP_URL` — не косметика. По ней приложение решает, отдавать ли
сгенерированные ссылки (в том числе на CSS и JS) по https. Пока сайт открыт по
`http` — например, по IP до выпуска сертификата, — `APP_URL` должен быть
`http://…`, иначе браузер пойдёт за стилями на 443-й порт, где никто не
слушает, и страница приедет без оформления, причём в логах nginx будет пусто:
запрос до него просто не дойдёт.

Там же выставьте `SESSION_SECURE_COOKIE=false` — иначе браузер не отдаёт куки
по http и вход молча не срабатывает. Обе переменные возвращаются к https-виду
сразу после сертификата.

Само «запрос пришёл по https» приходит в PHP из nginx: в `snippets/app.conf`
выставляется `fastcgi_param HTTPS`. Без него Laravel считал бы соединение
незащищённым и снимал бы флаг `secure` с сессионной куки даже на https.

Миграции выполняются при каждом старте контейнера. Это удобно для одной
реплики; если реплик будет несколько, вынесите `php artisan migrate --force` в
отдельный шаг деплоя, чтобы они не стартовали параллельно.

Стек рассчитан на обычный Docker, а не на Swarm. Если Portainer управляет
Swarm-кластером, учтите: `build:` там не поддерживается совсем, `depends_on` с
условием игнорируется, а `restart: unless-stopped` нужно заменить на
`deploy.restart_policy`. Порядок старта при этом не пострадает — entrypoint сам
ждёт базу в цикле, — но образы придётся брать только из реестра.

## Запуск без Docker

Нужны PHP 8.3+, Composer и Node. База — SQLite, Redis не требуется.

```bash
composer install
npm install

cp .env.example .env
php artisan key:generate

# переключить на SQLite
sed -i 's/^DB_CONNECTION=mysql/DB_CONNECTION=sqlite/' .env
sed -i 's/^SESSION_DRIVER=redis/SESSION_DRIVER=database/' .env
sed -i 's/^CACHE_STORE=redis/CACHE_STORE=database/' .env
sed -i 's/^QUEUE_CONNECTION=redis/QUEUE_CONNECTION=database/' .env

touch database/database.sqlite
php artisan migrate --seed
php artisan storage:link

npm run build
php artisan serve
```

## Как это устроено

| Слой | Где | Что делает |
| --- | --- | --- |
| Actions | `app/Actions` | Один инвокабельный класс на сценарий: каталог, корзина, авторизация, заказы |
| Модели | `app/Models` | `Customer`, `Category`, `Product`, `Cart`, `CartItem`, `Order`, `OrderItem` |
| Enum'ы | `app/Enums` | Статусы товара и заказа, статус и способ оплаты, сортировка каталога |
| Оплата | `app/Payments` | `PaymentGateway` + реализация-заглушка |
| API | `routes/api.php` | JSON под `/api`, внутри web-группы (сессия + CSRF) |
| Витрина | `resources/js` | Vue 3 SPA, отдаётся из `resources/views/storefront.blade.php` |
| Админка (API) | `routes/admin.php` | JSON под `/admin/api`, guard `admin` |
| Админка (UI) | `resources/js/admin` | Отдельное Vue-приложение, отдаётся из `resources/views/admin.blade.php` |
| Docker | `docker/`, `docker-compose.yml` | nginx, php-fpm (с Composer и Node внутри), MySQL, Redis |
| Палитра | `resources/css/app.css` | `ink-*` (чёрный хром и текст) и `gold-*` (акцент) в блоке `@theme` |
| Фото товаров | `app/Actions/Admin/Images`, диск `FILESYSTEM_DISK` | Загрузка, удаление, выбор обложки |

Аккаунт покупателя — единственный тип пользователя в приложении, поэтому таблица
называется `customers`, а модель — `Customer`; отдельного `User` нет.

Гостевая корзина живёт по токену в сессии и сливается в корзину покупателя при
входе и при регистрации, так что товары, отложенные до логина, не теряются.

Заказ хранит снимок позиции (название, slug, цена на момент покупки), поэтому
последующие правки каталога не переписывают уже оформленные заказы. Товары
блокируются (`lockForUpdate`) внутри транзакции оформления, чтобы два
одновременных заказа не продали один и тот же последний экземпляр.

Цены хранятся в минорных единицах (копейках) целым числом вместе с кодом валюты.

## Админка

`http://localhost:8000/admin`. Учётка заводится сидером из `.env`:

```
SHOP_ADMIN_EMAIL=admin@example.com
SHOP_ADMIN_PASSWORD=Password1
```

Пароль по умолчанию годится только для локального запуска — перед деплоем его
нужно поменять и прогнать `php artisan db:seed --class=AdminSeeder`.

Что умеет:

- **Категории** — создание, переименование, удаление. Категорию с товарами
  удалить нельзя (409). Порядок в списке — это порядок категорий в каталоге:
  стрелки ↑/↓ переставляют категорию относительно соседа и заодно перенумеровывают
  список в 1..N, так что дыры и одинаковые позиции сами приводятся в порядок.
  Точное число можно задать и руками в форме категории.
- **Товары** — создание и правка в любом статусе (черновик, опубликован, архив),
  фильтры по категории и статусу, поиск по названию и slug. Товар, попавший хотя
  бы в один заказ, не удаляется — его можно только перевести в архив.
- **Галерея товара** — загрузка нескольких фото сразу, удаление и выбор обложки:
  именно она показывается на карточке в каталоге. Первое загруженное фото
  становится обложкой само, а если удалить текущую — обложкой станет следующее
  фото, так что каталог не остаётся с заглушкой, пока есть хоть одна картинка.
- **Покупатели** — поиск, фильтр «заблокированные / активные», правка контактов,
  сброс пароля, блокировка и разблокировка.
- **Статистика** — стартовый экран: заказы по статусам, выручка по оплаченным,
  средний чек, новые покупатели, график заказов по дням за 7/30/90 дней или всё
  время, топ продаваемых товаров за период и топ просматриваемых за всё время.
- **Заказы** — список с фильтром по статусу, просмотр позиций, ручное создание
  заказа за покупателя, правка статусов и контактов, удаление. Перевод в
  «отменён» и удаление возвращают остатки товарам; отменённый заказ обратно в
  работу не возвращается (409).

Slug у категорий и товаров выводится из названия, если не задан явно, и
проверяется на уникальность до записи в БД.

### Администраторы и покупатели

Это два разных guard'а (`web` для покупателей, `admin` для админов) над двумя
таблицами: пароль покупателя не открывает панель, а пароль админа — витрину.
Оба guard'а живут в одной сессии, поэтому выход из одного не выкидывает второго
из того же браузера.

### Блокировка

Блокировка бьёт по всем путям сразу: заблокированный покупатель не войдёт
(403 вместо сессии), уже открытая сессия обрывается на первом же запросе,
cookie «запомнить меня» не воскрешает аккаунт, корзина и оформление заказа
закрыты. Разблокировка возвращает доступ.

### Фотографии

Файлы кладутся на диск из `FILESYSTEM_DISK` (по умолчанию `public`, то есть
`storage/app/public`, отдаётся через симлинк `public/storage`). URL строится
относительным (`/storage/...`), поэтому галерея работает за любым хостом,
портом и прокси. Переезд на S3 — это смена `FILESYSTEM_DISK`, менять код не
нужно: и действия, и модель ходят на диск по умолчанию.

Ограничения задаются в `.env`:

```
SHOP_MAX_PRODUCT_IMAGES=10
SHOP_MAX_IMAGE_KILOBYTES=5120
```

Принимаются JPG, PNG, WEBP и AVIF.

### Просмотры товаров

Открытие карточки товара на витрине увеличивает `products.views` на единицу —
атомарным `UPDATE`, поэтому одновременные открытия не теряются. Уникальность не
проверяется: это счётчик открытий, а не посетителей. Счётчик виден в списке
товаров и в статистике, недоступен для массового присвоения и не отдаётся в
публичном API товара. Листинг каталога просмотром не считается — только
открытие карточки.

Кроме счётчика на товаре, каждое открытие пишется в `product_view_daily` —
строка на товар и день. Из неё строится график «Просмотры товаров по дням» в
статистике; топ просматриваемых по-прежнему считается по счётчику за всё время.

## Контент витрины

Тексты и оформление витрины редактируются в админке, а не в коде.

- **Страницы** (`/admin/pages`) — статические страницы: «Вопрос-ответ», «Доставка
  и оплата», «Обучение», «Контакты». Slug выводится из заголовка, текст хранится
  как HTML. Порядок задаёт позицию в верхнем меню и в колонке «Информация» в
  футере.
- **Сайт** (`/admin/site`) — логотип, баннер над каталогом (картинка, заголовок,
  ссылка кнопки), блок над футером и обе правые колонки футера.

Логотип выводится в шапке и в футере вместо названия магазина; пока он не
загружен, там остаётся текст. В шапке он масштабируется до высоты 36 пикселей,
так что исходник удобнее брать вдвое-вчетверо больше и с прозрачным фоном —
фон под ним тёмный. Форматы те же, что у фотографий товаров: JPG, PNG, WEBP,
AVIF. SVG не принимается намеренно: он отдавался бы с того же домена и мог бы
выполнить скрипт в контексте сайта, в отличие от HTML в текстах, который
вставляется через `innerHTML` и скрипты не запускает.

У страницы три состояния видимости (`App\Enums\PageVisibility`):

| Состояние | В меню и футере | По прямой ссылке |
| --- | --- | --- |
| `published` — «В меню и по ссылке» | да | да |
| `unlisted` — «Только по ссылке» | нет | да |
| `draft` — «Черновик» | нет | нет (404) |

`unlisted` — страница для рассылки или для конкретного покупателя: ссылки на неё
нет нигде, но адрес работает. Форма показывает готовый адрес, как только страница
сохранена. Скрытость держится на том, что адрес никто не публикует: страница
отдаётся без авторизации, и угадавший slug её откроет. Для настоящего ограничения
доступа нужна отдельная проверка, её нет.

Три блока правятся визуальным редактором (TinyMCE 6, MIT) — текст страницы, блок
над футером и контакты в футере: заголовки, списки,
ссылки, цитата в рамке, таблицы, видео, картинки с загрузкой на сервер. Кнопка
**`<>`** («Исходный HTML») открывает диалог с разметкой — вставленное там
сохраняется как есть: редактор собран с `valid_elements: '*[*]'` и
`verify_html: false`, поэтому он не выбрасывает незнакомые теги, классы и
атрибуты. Интерфейс редактора переведён словарём `resources/js/admin/tinymceRussian.js`
(языковых пакетов TinyMCE в npm-пакете нет).

Рамка вокруг текста — это `<blockquote>` (кнопка «Цитата в рамке») или любой
элемент с классом `callout`. Стиль задан один раз в `resources/css/app.css`
(`.prose-page`) и продублирован для тела редактора в
`resources/css/editor-content.css`, поэтому в админке видно ровно то, что
получится на витрине.

**Содержимое страниц хранится и отдаётся как есть, без очистки.** Это осознанное
решение: редактор визуальный, и всем, у кого есть доступ в админку, доверена
произвольная разметка. Практическое следствие — администратор может разместить
на витрине любой код, поэтому доступ в админку равносилен доступу к сайту
целиком. Оговорка: `<script>` через такую вставку всё равно не выполнится —
браузер не запускает скрипты, попавшие в страницу через `innerHTML`; iframe,
таблицы и стили работают.

Картинки из редактора складываются в `content/` на том же диске и не привязаны
к товарам, поэтому удаление товара их не трогает. Разовую уборку накопившегося
делает `php artisan content:prune`: без аргументов он показывает список
неиспользуемых файлов с размерами, удаляет только с `--force`. Осторожность не
лишняя — полный обход папки видит и картинку, которую прямо сейчас загрузили в
черновик. Автоматически убирает их
`PurgeOrphanedContentImages`: после сохранения страницы, удаления страницы и
сохранения настроек он берёт адреса из текста, который только что заменили, и
удаляет те, на которые больше не ссылается ни одна страница и ни одно поле
настроек. Свежезагруженная картинка, ещё не попавшая ни в один сохранённый
текст, под сверку не попадает и остаётся на месте — иначе черновик, который
редактируют в соседней вкладке, терял бы картинки.

Две левые колонки футера собираются сами: «Пептиды» — десять случайных
опубликованных товаров, «Каталог» — категории (ссылка открывает каталог уже с
фильтром). Две правые — «Информация» и «Контакты» — свободные HTML-блоки из
настроек: пункты набираются вручную, поэтому туда помещается что угодно —
мессенджеры, часы работы, адрес, ссылки на скрытые страницы. Пустой блок убирает
колонку целиком.

Обратите внимание: «Информация» больше не следит за списком страниц. Новая
страница попадёт в верхнее меню, но в футер её нужно добавить руками. Миграция
переносит туда текущие опубликованные страницы, так что после обновления футер
выглядит как раньше.

Футер тёмный, поэтому у него своя типографика (`.prose-footer` в
`resources/css/app.css`): жирный текст выводится белым, ссылки подсвечиваются
золотым. Ссылки внутри всех редактируемых блоков перехватываются
`useInternalLinkNavigation` — внутренний адрес открывается роутером, без
перезагрузки приложения.

Начальное наполнение создаёт `SiteContentSeeder`: он добавляет четыре страницы и
заполняет пустые настройки один раз, через `firstOrCreate`, поэтому повторный
запуск на деплое не затирает правки редактора. Контакты и дисклеймер там —
плейсхолдеры, их нужно заменить своими: дисклеймер о назначении продукции
описывает конкретный бизнес и должен быть составлен под вас.

## Доставка

Два способа, и ведут они себя по-разному.

**Курьером** — покупатель просто пишет адрес, стоимость доставки в заказе равна
нулю и при необходимости проставляется вручную в админке.

**СДЭК** — всё считает перевозчик через API v2. Покупатель выбирает город
(подсказки идут из справочника СДЭК), затем «в пункт выдачи» или «до двери»;
для пункта выводится список ПВЗ, для двери остаётся поле адреса. Дальше шоп
спрашивает у СДЭК тарифы для этого направления и веса корзины и показывает их
ценой и сроком. Выбранный тариф добавляется к сумме заказа.

**Цена, пришедшая из браузера, не используется.** В момент оформления
`PriceDelivery` спрашивает перевозчика заново и берёт его ответ; если
выбранного тарифа в этом ответе нет — заказ не создаётся. Так же проверяется и
пункт выдачи: он должен принадлежать выбранному городу. Иначе цену доставки
можно было бы занизить, отредактировав запрос.

Вес посылки — сумма весов товаров (`weight_grams` в карточке товара). У товара
без веса берётся `SHOP_DEFAULT_PRODUCT_WEIGHT_GRAMS`, и посылка никогда не
весит меньше этого значения: расчёт невесомой посылки перевозчик не примет.

Что нужно в `.env`: `CDEK_ACCOUNT`, `CDEK_PASSWORD` и `CDEK_FROM_CITY_CODE`
(код города отправления). Без них раздел доставки честно отвечает, что
интеграция не настроена, вместо пятисотки. Токен живёт в кэше 50 минут и
перезапрашивается сам, в том числе если СДЭК отозвал его раньше.

Контур переключается одной переменной: `CDEK_TEST=true` — тестовый
(`api.edu.cdek.ru`), `false` — боевой (`api.cdek.ru`). Адрес выводится из неё,
руками его задавать не нужно; `CDEK_BASE_URL` остаётся только для подмены на
локальную заглушку.

**У контуров разные учётные записи.** Тестовую СДЭК публикует в документации,
боевую выдаёт вместе с договором. Самая частая ошибка при подключении —
тестовые ключи на боевом адресе: СДЭК отвечает, что учётные данные отклонены.

Какой контур включён, видно в админке: «Сайт» → «Интеграции». Там же состояние
приёма оплаты — ЮKassa помечает ключ тестового магазина префиксом `test_`, по
нему это и определяется.

Тарифы на тестовом контуре выдуманные, но структура ответа настоящая: проверять
на нём стоит механику, а не цены.

Что **не** сделано: заказ в ИС СДЭК не регистрируется (метод «Регистрация
заказа»), накладные и вызов курьера не создаются, вебхуки статусов не
принимаются. Сейчас интеграция только считает и показывает.

## Оплата

Подключена ЮKassa, сценарий с редиректом: шоп открывает платёж, отправляет
покупателя на страницу подтверждения и узнаёт результат из вебхука, а не из
того, что браузер вернулся.

Включается двумя переменными:

```
YOOKASSA_SHOP_ID=
YOOKASSA_SECRET_KEY=
```

Пока их нет, `PaymentGateway` остаётся связан с `PendingPaymentGateway`: заказы
оформляются, а страница оплаты честно сообщает, что провайдер не подключён.
Переключение автоматическое, правки кода не нужны.

**Вебхук — `POST /api/payments/yookassa/webhook`.** Его адрес указывается в
личном кабинете ЮKassa (события `payment.succeeded` и `payment.canceled`).
ЮKassa ничего не подписывает, поэтому тело уведомления считается слухом: из
него берётся только идентификатор платежа, а сам платёж читается обратно
запросом к ЮKassa с нашими ключами. Подделанное уведомление ничего не двигает —
это покрыто тестом. Маршрут исключён из проверки CSRF, потому что приходит он от
сервера, а не из браузера с сессией.

Повторное уведомление не двигает `paid_at`: ЮKassa шлёт их несколько раз, пока
не получит 200. Неизвестный заказ тоже подтверждается двухсоткой — иначе ЮKassa
будет ретраить сутки.

Ключ идемпотентности привязан к заказу, поэтому двойной клик по «Оплатить»
открывает тот же платёж, а не второй.

Отменённый заказ не воскресает от позднего успешного платежа: статус оплаты
записывается, статус заказа остаётся «Отменён» — деньги в этом случае возвращает
человек, автоматического возврата нет.

**Чек по 54-ФЗ отправляется вместе с платежом.** Магазину с подключённой
фискализацией ЮKassa иначе отвечает «Receipt is missing or illegal». В чек
попадают позиции заказа и доставка отдельной строкой, так что сумма чека
сходится с суммой платежа. Ставка НДС — `YOOKASSA_VAT_CODE` (по умолчанию 1,
«без НДС»), система налогообложения — `YOOKASSA_TAX_SYSTEM_CODE` (нужна, только
если их несколько). Если фискализации нет, `YOOKASSA_RECEIPT=false` выключает
чек целиком.

Чего нет: возвратов (`/refunds`), сохранённых карт и рекуррентов.

## Раздел в разработке

Галочка «Раздел в разработке» у категории (админка → «Категории»). Что она
делает:

- в каталоге вместо товаров появляется «Раздел находится в разработке»;
- в списке категорий у раздела вместо счётчика стоит пометка — счёт обещал бы
  товары, которых покупатель там не увидит;
- товары раздела не показываются **нигде**: ни в общем каталоге, ни в поиске,
  ни в колонке футера, ни в карте сайта.

Последнее важно: без этого витрина предлагала бы купить товар из раздела, о
котором сама пишет, что его ещё нет. В админке товары раздела видны как
обычно — иначе его нечем было бы наполнять.

Галочку снимают, когда раздел готов; ничего восстанавливать руками не нужно.

## Категория по умолчанию на главной

Админка, «Сайт» → «Каталог» → «Категория по умолчанию на главной». Каталог
открывается на ней, пока покупатель не выбрал другую; «Все товары» возвращает
прежнее поведение.

Хранится ссылкой на категорию, а не её адресом, поэтому переименование
категории настройку не ломает. Удаление категории сбрасывает настройку на «Все
товары» — витрина не остаётся с фильтром, по которому ничего нет.

## Валюта товара и курс ЦБ

Цена назначается в валюте товара — рубли или доллары, выбор рядом с полем цены
в админке, «Товары» → карточка товара.

Магазин при этом **рассчитывается в одной валюте** (`SHOP_CURRENCY`, по
умолчанию рубли): эквайринг принимает рубли, и сумма заказа должна совпадать с
тем, что спишут. Поэтому:

- в каталоге и на странице товара цена показывается в своей валюте, а рядом —
  «≈ столько-то ₽ при оплате»;
- корзина считается в рублях, у долларовой строки видно и ценник, и пересчёт;
- в заказ попадает рублёвая сумма, а позиция запоминает исходную цену, валюту
  и курс — иначе через неделю сумму будет нечем объяснить.

Курс берётся у ЦБ (`https://www.cbr.ru/scripts/XML_daily.asp`) и кэшируется на
сутки — публикуется он раз в день. Если ЦБ не ответил, используется последний
известный курс (хранится 30 дней) и пишется предупреждение в лог. Если
известного курса нет вовсе, магазин **отказывается оформлять** заказ с товаром
в валюте, вместо того чтобы посчитать по выдуманному числу.

| Переменная | По умолчанию |
| --- | --- |
| `CBR_URL` | `https://www.cbr.ru/scripts/XML_daily.asp` |
| `CBR_TIMEOUT` | `8` |

Наценки к курсу нет: пересчёт идёт ровно по ЦБ. Если понадобится спред —
это одно место, `ConvertMoney`.

## Деплой не трогает контент

Наполнение из `database/seeders` выполняется при каждом старте контейнера, но
только для пустого места:

| Что | Когда наливается |
| --- | --- |
| Каталог | только если в нём нет ни одного товара |
| Страницы | только если нет ни одной |
| Настройки сайта | только пустые поля (новая настройка получает значение по умолчанию) |
| Администратор | только если его ещё нет |

Правки в админке — названия, описания, цены, валюта, остатки, тексты страниц —
деплой переживают. Удалённый товар или страница обратно не возвращаются.

Залить исходный список заново — осознанное действие: очистить таблицу
`products` (и `categories`, если нужно), после чего перезапустить контейнер с
`SEED_CATALOG=true`.

Пароль администратора переменной `SHOP_ADMIN_PASSWORD` задаётся только при
создании и больше не переписывается. Забыли — сбросить командой:

```bash
docker compose exec app php artisan admin:password support@agelesscode.store новый-пароль
```

## Оптовые условия и минимум в заказе

Задаются на категории, в админке → «Категории»:

- **Только для оптовых закупок** — подпись у цены в каталоге и на странице товара;
- **Минимум в заказе** — меньше этого количества товар нельзя положить в корзину и заказать.

Значения по умолчанию проставлены миграцией: минимум 10 шт. для всего, кроме
Wellness-устройств, и оптовая подпись у Пептидов, Витаминов, Инъекционных
препаратов и Ингаляторов. Дальше меняется в админке.

Ограничение живёт на сервере, а не в вёрстке: при попытке положить меньше
магазин отвечает «Товар «…» продаётся от N шт.». На админа оно не
распространяется — заказ, заведённый вручную, оформляется на любое количество.

## Онлайн-оплата и СДЭК: выключатели

| Переменная | По умолчанию | Что делает |
| --- | --- | --- |
| `SHOP_ONLINE_PAYMENT_ENABLED` | `false` | `true` возвращает приём оплаты через ЮKassa |
| `SHOP_CDEK_ENABLED` | `false` | `true` возвращает доставку СДЭК |

Выключено — не то же самое, что «не настроено»: ключи остаются на месте,
интеграция просто не предлагается покупателю и не принимается на оформлении.
В админке, «Сайт» → «Интеграции», такое состояние показывается как
«Отключена» (а не «Не настроена»). Чтобы вернуть — поставить `true` и
перезапустить стек.

Пока онлайн-оплата выключена, на оформлении остаются только офлайновые
способы, а после заказа покупатель видит: «Ваш заказ принят. С вами свяжется
менеджер для подтверждения заказа и согласования деталей.»

## Уведомления о заказах

При оформлении уходит два письма: покупателю — подтверждение, магазину — на
`SHOP_ORDERS_EMAIL`. Пусто — письмо магазину не отправляется, покупателю
уходит всё равно.

```
MAIL_HOST=smtp.beget.com      MAIL_PORT=465      MAIL_SCHEME=smtps
MAIL_USERNAME=support@agelesscode.store
MAIL_PASSWORD=…
MAIL_FROM_ADDRESS=support@agelesscode.store
SHOP_ORDERS_EMAIL=support@agelesscode.store
```

Если провайдер режет 465 — `MAIL_PORT=2525` и `MAIL_SCHEME=smtp`.

Письма отправляются через очередь, поэтому в стеке есть сервис `queue`. Если
его остановить, письма будут копиться в redis и не уйдут.

Дополнительно заказ можно дублировать в Telegram — `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_CHAT_ID`. Пусто — ничего не отправляется. Ошибка Telegram пишется в
лог и не влияет на заказ.

`TELEGRAM_CHAT_ID` — это личный чат (положительное число), группа
(отрицательное) или супергруппа (`-100…`). Минус — часть адреса, кавычки в
Portainer не нужны, значение подставляется как есть.

Проверить бота:

```bash
docker compose exec app php artisan telegram:test
```

Команда говорит, что именно не так: не задан токен, не задан chat_id (и тогда
показывает список чатов, о которых бот знает, с их id), Telegram недоступен с
сервера, или чат не найден. При успехе в чат приходит тестовое сообщение.

Если `telegram:test` отвечает «Telegram недоступен: cURL error 28» — до
Telegram с сервера нет сети. Частая история у российских хостингов, кодом не
обходится. Два пути:

| Переменная | Что указывать |
| --- | --- |
| `TELEGRAM_PROXY` | `socks5://user:pass@host:1080` или `http://host:3128` — запрос пойдёт через прокси, токен остаётся у вас |
| `TELEGRAM_API_URL` | адрес зеркала Bot API вместо `https://api.telegram.org` |

Прокси предпочтительнее: чужое зеркало Bot API видит и токен бота, и все
сообщения. На письма о заказах это всё не влияет — они идут своим путём.

**MTProto-прокси (server / port / secret) сюда не подходит.** Это протокол
самого приложения Telegram; обычный HTTPS-запрос на Bot API через него не
идёт, вписать secret некуда.

Если ни прокси, ни зеркала нет, своё зеркало поднимается бесплатно на
Cloudflare Workers — тогда токен проходит только через вашу же страницу:

```js
export default {
    async fetch(request, env) {
        const url = new URL(request.url)

        // Пускаем только свой токен, иначе воркер станет открытым прокси.
        if (! url.pathname.startsWith(`/bot${env.BOT_TOKEN}/`)) {
            return new Response('not found', { status: 404 })
        }

        url.protocol = 'https:'
        url.hostname = 'api.telegram.org'
        url.port = ''

        return fetch(new Request(url, request))
    },
}
```

Адрес воркера (`https://…workers.dev`) прописывается в `TELEGRAM_API_URL`.

## Остатки

Витрина не показывает точное число и не получает его от сервера вовсе:
`ProductResource` отдаёт `stock_level` и `stock_label` вместо `stock`.

| Остаток | Что видит покупатель |
| --- | --- |
| 0 | Нет в наличии |
| 1 | Последний |
| 2–10 | Мало |
| 11–20 | Достаточно |
| больше 20 | Много |

Пороги живут в `App\Enums\StockLevel`. В админке остаток остаётся обычным
числом — она работает с другим ресурсом (`App\Http\Resources\Admin`).

Раз браузер больше не знает остаток, поле количества ограничено не им, а общим
лимитом магазина (`SHOP_MAX_ITEM_QUANTITY`, приезжает в `/api/site`). Количество
сверх остатка отклоняет сервер — `AddCartItem` и `UpdateCartItemQuantity`
отвечают 422 и сообщением «Товар «…» недоступен в запрошенном количестве».

## SEO

Витрина рисуется в браузере, поэтому краулер, который не исполняет скрипты,
видит только пустую оболочку и то, что сервер положил в `<head>`. Поэтому
`<head>` собирается на сервере для любого адреса витрины, а не только для
главной.

`App\Actions\Seo\ResolvePageMeta` разбирает путь и возвращает `PageMeta` —
заголовок, описание, canonical, картинку и микроразметку:

| Адрес | Что отдаётся |
| --- | --- |
| `/` | заголовок и описание из админки, JSON-LD `Store` |
| `/products/{slug}` | имя и краткое описание товара, JSON-LD `Product` с ценой, валютой и наличием (`InStock` / `OutOfStock`) |
| `/pages/{slug}` | заголовок страницы и текст, очищенный от разметки |
| всё остальное | `noindex, follow` |

Под «всё остальное» попадают корзина, оформление, заказы, вход, регистрация —
и, намеренно, скрытые страницы (`unlisted`) и черновики товаров: открыть по
ссылке можно, в выдачу они не попадут. Админка отдаёт `noindex, nofollow`
отдельным тегом в своём шаблоне.

Заголовок и описание главной редактируются в админке: «Сайт» → «Поисковая
выдача». Пусто — берётся заголовок блока над футером, потом `SHOP_BRAND`.

`/sitemap.xml` собирается на лету (`App\Actions\Seo\BuildSitemap`): главная,
разделы каталога, опубликованные страницы и товары. Скрытая страница и
черновик в карту не попадают — перевод страницы в «Опубликована» добавляет её
без пересборки чего-либо.

`/robots.txt` отдаётся маршрутом, а не файлом: строка `Sitemap:` должна
содержать абсолютный адрес, а он зависит от домена. Статического
`public/robots.txt` нет намеренно — файл на диске перехватил бы маршрут.

После загрузки приложение меняет `<title>` само (`resources/js/documentTitle.js`)
— иначе в закладку и в историю попал бы заголовок той страницы, с которой
начали. Значения по умолчанию оно берёт из `<meta name="site-title">` и
`<meta name="site-brand">`, то есть из тех же настроек админки, а не из
зашитой в код строки.

## Вход и регистрация

Пароль — не короче `SHOP_PASSWORD_MIN_LENGTH` (по умолчанию 5), больше никаких
требований: ни заглавной буквы, ни цифры. Правило задано один раз через
`Password::defaults()` и действует и при регистрации, и при смене пароля
администратором.

В полях пароля есть кнопка «показать» — на витрине и в админке.

Телефон приводится к одному виду `+7 XXX XXX XX XX`. Вводить можно как
привычно: `8 999 …`, `+7(999)…`, десять цифр подряд — и маска в поле, и
`App\Support\PhoneNumber` на сервере приведут к одному результату. Всё, что не
складывается в российский номер, отклоняется валидацией. Это касается и
регистрации, и оформления заказа, и форм в админке.

## Грабли

Список для тех, кто вернётся к проекту позже (в том числе для новой сессии
Claude без истории переписки). Каждый пункт стоил отладки.

**Метод FormRequest нельзя называть по имени поля, которое он валидирует.**
Аксессор `image()` в реквесте с полем `image` уходит в бесконечную рекурсию и
роняет процесс PHP без внятной ошибки. Отсюда `bannerImage()` и
`uploadedImage()` в `UploadBannerImageRequest` и `UploadContentImageRequest`.
Имя `images()` при поле `images` при этом безопасно.

**Один guard на два входа — одна сессия.** Витрина (`web`) и админка (`admin`)
делят cookie. Выход покупателя не имеет права звать `invalidate()` или
`regenerate()`: первое выкидывает администратора, второе гонится с параллельными
запросами, которые страница шлёт при загрузке. `LogoutCustomer` чистит только
своё состояние и обновляет CSRF-токен.

**Guard по умолчанию — изменяемое глобальное состояние.** `auth:admin` меняет
его на весь запрос, и действие витрины, написанное на `Auth::user()`, начинает
отвечать администратором. Поэтому guard'ы резолвятся по имени через
`App\Enums\Guard`, а в тестах `signInAdmin()` возвращает default обратно на
`web`.

**`Resource::collection(MissingValue)` рендерится как `[]`, а не пропускается.**
Из-за этого все заказы в админке выглядели без позиций. Правильная форма —
`whenLoaded($rel, fn () => Resource::collection(...))`.

**Порядок утилит Tailwind 4 задаётся порядком объявления в `@theme`.** Активная
кнопка `bg-gold-400` проигрывала `hover:bg-ink-900`, потому что `ink` объявлен
раньше. Лечится не `!important`, а тернарником с активным hover-классом.

**`URL::forceHttps()` нельзя вешать на `isProduction()`.** Сайт, открытый по IP
без сертификата, получал https-ссылки на ассеты, и запросы до nginx просто не
доходили — логи при этом пустые. Схема берётся из `APP_URL`, поведение закрыто
тестом `GeneratedUrlSchemeTest`.

**`public/storage` создаётся на сборке образа, а не на старте.** `public/`
принадлежит root, контейнер работает под www-data, поэтому `storage:link` в
энтрипоинте падал в цикле рестартов. В Dockerfile ссылка делается относительной
и от root, а `public/storage` лежит в `.dockerignore` — локальный симлинк
абсолютный и в образ попадать не должен.

**Portainer собирает образ только если его нет.** Кнопка «Re-pull image» на
локально собранном образе даёт `pull access denied`. Чтобы подхватить новый код,
старый образ нужно удалить; `docker-compose.build.yml` задаёт `pull_policy: build`.

**TinyMCE шлёт `SetContent` во время инициализации.** Если сразу транслировать
это наверх, поле очищается до того, как в редактор попадёт исходное значение —
и текст страницы пропадает при открытии. Компонент молчит, пока не применит
начальный HTML.

**Переменная, заданная в стеке, сама в контейнер не попадает.** Compose
передаёт сервису только то, что перечислено в его `environment`. Ключи СДЭК и
ЮKassa были заданы в Portainer, но отсутствовали в этом списке — приложение их
не видело и сообщало, что интеграции не настроены. Проверяется тестом
`ProductionEnvironmentTest`: каждая переменная, которую читают `config/shop.php`
и `config/services.php`, должна быть в `environment` сервиса `app`.

**Плейсхолдеры контактов должны быть валидными.** Сид с адресом `ххххх@example.com`
(кириллицей) молча блокировал отправку формы настроек: браузер отменял submit по
`type=email` без единого сообщения. Форма помечена `novalidate` — ошибки
показывает сервер.
